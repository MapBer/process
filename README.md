# Linux process exercises in C

These exercises progress from basic process identification to interprocess communication through pipes, shared memory, signals, and TCP sockets. Each directory contains a `README.md` describing the exercise and a commented solution in `main.c`. The `main.c` file in the project root is separate from these exercises.

## LAN chat

Exercise 12 contains two standalone source files. Build both from the project root:

```bash
make -C exercises 12_tcp_chat
```

On the server computer, find its LAN IPv4 address with `ip -4 addr`.
For example, if that address is `192.168.1.10`, start:

```bash
./exercises/bin/12_tcp_chat_server 192.168.1.10 5050
```

On another computer on the same network, build the client and connect using
the **server's** address and the same port:

```bash
./exercises/bin/12_tcp_chat_client 192.168.1.10 5050
```

Replace the example address with the actual server address. If a firewall is
active, allow inbound TCP on the chosen port on the server. Both users can type
messages and press Enter at any time. Ctrl+D finishes sending while still
allowing incoming messages; the chat exits once both sides finish sending.
Ctrl+C exits immediately. The server accepts one client per run. Messages are
plain text without encryption. For testing on one computer, use `127.0.0.1`
in both commands and run them in separate terminals.

```bash
./exercises/bin/01_pid_ppid

# Remove the executables generated by this Makefile
make -C exercises clean
```

## General tips

- `fork()` returns -1 on error, 0 in the child, and the child's PID in the parent.
- Check system call errors and use `perror()` to report the cause.
- Parents should reap their children using `wait()` or `waitpid()`.
- If `waitpid()` returns -1 with `errno == EINTR`, retry; handle other errors separately.
- Use `WEXITSTATUS(status)` only when `WIFEXITED(status)` is true.
- Before `fork()`, call `fflush(NULL)` if you have buffered stdio output, to avoid duplicating pending output.
- Exercises 1 and 7 use `sleep()` for observation. Use `waitpid()` when you need to wait for a child to finish.

Read local documentation with `man 2 fork`, `man 2 waitpid`, `man 3 exec`, and `man 2 pipe`.

## Understanding the results

1. **PID/PPID:** The PID identifies the current process, and the PPID identifies its parent. The parent is often a shell or the program launching the exercise. PIDs can be reused. Exercise 1 stays alive for 20 seconds for observation.
2. **fork:** Both processes continue after `fork()`. The scheduler determines their execution order. Placing `waitpid()` after the parent's print statement ensures that the parent reaps the child before exiting; it does not determine which process prints first.
3. **Memory:** The child changes its own copy of `count`. `waitpid()` waits for termination; it does not copy the child's variables back to the parent.
4. **Process count:** Three successful consecutive `fork()` calls in every process produce 8 processes in total, including 7 new processes, and 8 `Hello` lines. For `n` such calls, the total is `2^n`, and the number of new processes is `2^n - 1`.
5. **Multiple children:** Only the parent continues the creation loop; each child returns immediately. Waiting in PID order does not determine execution order. Exit statuses 1, 2, and 3 are deliberately chosen results in this exercise.
6. **exec:** A successful exec replaces the program while preserving its PID and never returns to the next statement. Run `./exercises/bin/06_exec nonexistent_command` to observe the error path and exit status 127.
7. **Zombie:** The child has terminated and no longer executes code. The system retains termination information until the parent reaps it using `waitpid()`. This exercise takes about 30 seconds.
8. **Pipe:** A reader receives EOF once all buffered data has been read and all write ends are closed. A child that keeps its own write end open may wait indefinitely. `read()` does not append a null terminator; the solution uses `fwrite()` with the actual byte count.
9. **Shared memory:** Parent and child access the same System V shared memory segment. The child changes the value from 10 to 15; the parent waits before reading it. The segment is marked for deletion and removed automatically once both processes detach.
10. **Signal:** The parent sends `SIGUSR1` to its child. Blocking the signal before `fork()` lets the child consume it reliably with `sigwait()`, even if it arrives early.
11. **TCP socket:** Independent server and client processes exchange greetings over localhost. TCP carries a byte stream; this example uses half-close and EOF to delimit the request and reply.
